# 脑机接口与 EEG 解码 RAG 知识库项目技术报告

本文档对脑机接口与 EEG 解码论文知识库项目进行技术可行性分析，并说明当前系统在论文归档、知识库构建、向量化、混合检索及 MCP 服务封装方面的实现原理。项目的目标是收集近年脑机接口与 EEG 研究论文，将论文内容转换为适合大语言模型处理的文本块，在本地建立可持续更新的知识库和向量库，并向智能体提供论文归档与知识检索能力。

## 1. 技术可行性分析

### 1.1 行业数据

本项目的数据主题为脑机接口与 EEG 解码，覆盖脑机接口系统、EEG 情绪识别与分类、跨被试 EEG 建模、EEG 多模态学习以及 EEG-to-text 等生成任务。脑机接口通过采集和解码神经活动，在大脑与外部设备之间建立信息通道，可用于辅助交流、运动控制、神经康复、认知状态检测和情绪计算等场景。EEG 具有非侵入、时间分辨率高、设备成本相对较低等特点，是非侵入式脑机接口研究中应用最广泛的信号形式之一。近年来，脑机接口在传感器、电极、信号处理和神经解码方面持续发展，相关论文具有较强的时效性。[1]

EEG 研究同时具有较高的知识密度。论文通常包含采集设备、受试者数量、电极布局、采样率、滤波范围、伪迹处理、时间窗口、频带特征、模型结构、数据划分和评价指标等大量技术信息。不同论文即使研究相同任务，也可能因为实验协议不同而得到差异明显的结果。例如，受试者依赖的随机划分通常不能直接代表跨被试泛化能力；使用不同通道数量、不同时间窗口或不同频带特征，也会改变模型输入和实验结论。因此，系统不仅需要保存论文的主题和摘要，还需要保留方法、预处理、数据集、实验设置、结果与局限等正文内容。

在 EEG 情绪识别方向，研究方法已经从时域、频域、时频域和非线性手工特征，发展到 CNN、循环神经网络、图神经网络和 Transformer 等深度学习模型。2024 年的相关综述表明，深度学习已经成为 EEG 情绪识别的重要研究路线，但数据规模有限、跨被试差异大和实验协议不统一仍是主要问题。[2] 近年的代表性研究包括使用 CNN 与 Transformer 交互建模局部和全局特征的 CIT-EmotionNet，以及融合 EEG、音频和视频的多模态情绪识别框架。这些工作说明 EEG 研究正在从单一分类任务向跨模态表示学习和更复杂的应用场景扩展。[3]

EEG-to-text 是更具前沿性的生成任务。NeurIPS 2023 的 DeWave 将 EEG 信号编码为离散表示，并与预训练语言模型对齐，尝试减少对词级事件标记的依赖。[4] ACL 2024 的 E2T-PTR 使用 EEG—文本对比学习与掩码自编码预训练，再利用语言模型完成文本解码。[5] 此类研究表明，非侵入式脑信号到文本的转换具有研究潜力，但现阶段仍受到 EEG 噪声、个体差异、数据规模、实验诱发方式和生成评估方法的限制。ACL 2026 的研究进一步指出，既有 EEG-to-text 方法经常依赖 teacher forcing，真实场景需要采用不依赖目标文本提示的评估方式，并处理 EEG 信号的不稳定性。[6] 因此，知识库必须保存论文时间、版本和完整实验条件，不能只记录论文给出的最终指标。

项目数据主要来源于会议论文集、期刊、arXiv、PubMed/PMC 以及论文作者公开的代码和数据集页面。arXiv 可以及时提供预印本及其版本信息，适合追踪最新研究，但预印本不等同于经过同行评议的正式论文。会议和期刊数据可以通过 DOI、会议官网和出版社页面核验，Crossref 可提供标题、作者、DOI、发表时间、期刊或会议信息等元数据，PubMed 与 PMC 可用于检索生物医学论文和开放全文。[7][8] 对同一研究同时存在 arXiv 版本和正式出版版本的情况，系统应建立版本关联，并优先使用正式出版信息作为主要记录。

论文采集范围可优先覆盖近三至五年，并补充经典方法、常用数据集和基础评价方法。检索词应包括“brain-computer interface”“BCI”“EEG”“EEG emotion recognition”“cross-subject EEG”“EEG-to-text”“brain-to-text”和“neural language decoding”等。数据采集过程需要遵守论文许可和版权要求，仅应归档开放获取、机构已授权或用户合法提供的全文。无法合法获得全文时，可以保存公开的题录信息和摘要，但不应绕过访问限制下载论文。

从数据特征看，脑机接口与 EEG 论文适合采用 RAG 建立知识服务。一方面，论文更新速度快，外部知识库可以独立增量更新，不需要重新训练大语言模型；另一方面，论文正文中包含大量可被分割和检索的技术描述，适合转换为文本块。系统在回答问题时只需要选取与问题最相关的若干文本段，而不需要把全部论文同时发送给大语言模型，从而降低上下文长度和计算资源需求。

### 1.2 RAG 知识检索

RAG，即检索增强生成，是一种将外部知识检索与大语言模型生成相结合的技术。大语言模型参数中保存的是训练期间形成的隐式知识，这些知识更新成本高，也难以直接给出来源。RAG 在模型生成答案之前，从外部知识库中检索与用户问题相关的内容，并将检索结果作为上下文提供给模型。经典 RAG 将生成模型视为参数化记忆，将文档索引视为非参数化记忆，从而使系统能够使用可独立更新和检查的外部知识。[9]

RAG 系统由离线知识库构建和在线知识检索两个过程组成。离线过程负责将原始论文解析为文本，完成清洗、分块、元数据添加和向量编码，并将处理结果写入可检索的存储系统。在线过程接收用户 query，对 query 和知识库文本块进行相关性计算，选出最相关的 top_k 个文本块。检索结果随后可以直接返回，也可以与用户问题一起交给 LLM，由 LLM 根据证据生成完整回答。

常见检索方法包括关键词检索、向量检索和混合检索。BM25 是典型的关键词检索方法，它根据查询词在文档中的词频、查询词在整个语料库中的稀有程度以及文档长度计算相关性。该方法适合检索数据集名称、模型缩写、电极名称、频带、指标和数值等精确术语。对于 EEG 论文中的 `SEED-IV`、`ZuCo`、`AF3`、`PSD`、`BLEU-4` 等内容，BM25 能够提供稳定且具有可解释性的关键词匹配结果。

向量检索使用 embedding 模型将 query 和文本块映射到同一个向量空间，再通过余弦相似度等方法衡量语义关系。它不要求 query 与文本块使用完全相同的词语，因此能够处理同义表达、自然语言改写和较复杂的问题。例如，中文问题中的“跨被试泛化”与英文论文中的“cross-subject generalization”在字面上不同，但合适的跨语言 embedding 模型仍可能将二者映射到相近位置。向量检索的效果取决于 embedding 模型的训练语言、领域适配程度和输入长度，不能脱离实际语料进行判断。

BM25 和向量检索具有互补关系。BM25 对精确词语敏感，但对同义表达的召回能力较弱；向量检索能够识别语义相似性，但可能弱化专有名词、数字和缩写。当前项目采用两者加权融合的混合检索方法，以向量检索负责语义召回，以 BM25 负责精确术语匹配。该方案适合 EEG 论文，因为用户问题往往同时包含自然语言意图和专业术语。

RAG 用于 EEG 知识检索在技术上是可行的，但需要注意语言与领域差异。当前系统默认使用 `bge-small-zh-v1.5`，而大部分 EEG 论文为英文。中文 query 与英文文本块之间属于跨语言检索，实际效果需要通过专门的 EEG 问答数据集验证。工程上可以比较英文模型、多语言模型和 query 翻译等方案，并以 Recall@k、MRR、nDCG 和证据命中率作为检索评价指标。RAG 只能为 LLM 提供外部证据，不能保证模型一定正确理解论文，因此检索结果还应保留论文来源、版本和文本位置，便于用户核查。

## 2. 技术细节

### 2.1 知识库构建

当前知识库构建流程由文档读取、文本清洗、初步语义分块、二次动态分块、元数据添加、知识库存储和向量库存储组成。相关实现位于 `corpus/documentProcess.py` 和 `HybridRetriever/Retriever.py`。

#### 2.1.1 PDF 提取与文本清洗

系统支持 PDF、TXT 和 DOCX 三种输入格式。归档开始时，系统首先验证文件路径是否存在、输入是否为单个文件以及扩展名是否受支持。PDF 读取依次尝试 `pypdf`、`PyPDF2` 和 `pdfplumber`，对每一页调用文本提取接口，并以空行连接不同页面。TXT 读取依次尝试 UTF-8 BOM、UTF-8 和 GB18030 等编码。DOCX 读取通过解压文档并解析 `word/document.xml` 完成。

PDF 提取结果通常包含由页面宽度造成的硬换行，不能直接把每一行作为一个自然段。系统首先统一 Windows 和 Unix 换行符，去除 BOM、零宽字符和不合理空白，再识别空行、标题、普通文本、列表、代码和表格。连续的普通文本行会根据字符边界重新合并为自然段；空行、标题和结构化内容则保留为段落边界。每个自然段保存正文、内容类型、来源路径、来源文件名、原始起止行和段落序号。

当前 PDF 处理依赖 PDF 自带的文本层，没有 OCR 和完整的版面分析能力。因此，普通文本型 PDF 可以直接处理，扫描件、复杂双栏论文、公式和图表可能出现内容缺失或顺序错误。这不影响系统总体方案的可行性，但会限制知识库输入质量。工程应用中需要在归档阶段增加文本质量检查，并为低质量 PDF 增加 OCR、版面恢复和页眉页脚清理。

#### 2.1.2 初步语义分块与二次动态分块

文本清洗完成后，系统以恢复后的自然段作为输入进行初步语义分块。系统使用本地 SentenceTransformer 模型计算相邻普通段落的语义相似度，默认阈值为 `0.72`。当相邻段落相似度达到阈值时，系统将其合并到同一个语义块；当相似度低于阈值时，系统结束当前语义块并开始新的分块。为了避免连续段落无限合并，每个语义块最多包含六个自然段。标题、代码、列表和表格等结构化段落不会按照普通文本的语义规则强行合并。

相似度阈值不是固定的最终参数。系统提供阈值校准功能，可以对样本文档中的相邻自然段计算相似度，输出相似度样本、P50、P75、P90 和 P95 等分位数，并给出建议阈值。项目可以通过人工抽查段落合并结果调整阈值，使分块更符合 EEG 论文的章节和论述结构。

初步语义分块用于保持相邻论述的完整性，但合并结果仍可能超过适合检索和 embedding 的长度，因此系统继续执行二次动态分块。普通文本使用 512 字符的窗口和 128 字符的重叠，表格使用 384 字符窗口和 96 字符重叠，代码使用 256 字符窗口和 64 字符重叠。重叠区域用于保留边界附近的上下文，减少模型名称、实验条件和结果被截断到不同 chunk 后造成的信息损失。

二次分块当前按照字符位置切分，不会优先选择句号、段落末尾或 token 边界。因此它能够保证 chunk 大小和重叠比例，但仍可能在句子中间截断。后续可以在不改变总体流程的前提下，把固定字符窗口调整为以目标长度为约束、以最近句界为切分位置的分块方法。

#### 2.1.3 元数据与知识库存储

每个最终 chunk 都会被添加唯一 ID 和完整元数据。元数据包含来源路径、来源文件名、原始自然段范围、原始行号范围、chunk 顺序、字符数量、内容类型、模型路径和创建时间。chunk ID 采用 UUID5 生成，并将来源路径、段落范围、chunk 顺序、模型路径和正文共同作为区分维度。相同内容在相同位置和模型条件下会得到稳定 ID，不同模型处理同一文档时则可以形成独立记录。

chunk 被写入 `data/corpus/corpus.db` 的 `chunks` 表。该表是知识库中唯一参与检索的正文入口，至少保存 chunk ID、来源、内容类型、顺序、正文、模型路径、元数据 JSON 和创建时间。保存时使用 `INSERT OR IGNORE`，已有相同主键的记录不会重复写入。

Retriever 在正式处理文档前还会进行来源去重。当前去重键由文件名去掉最后一个扩展名后转换为小写得到，并且只在当前模型路径下检查。相同来源键和相同模型不会重复归档，不同模型处理相同文档则被视为不同结果。该规则可以处理一般的重复提交，但不能准确区分不同目录中的同名论文。面向正式论文库时，应增加 DOI、arXiv ID、标题规范化和文件哈希等去重依据。

#### 2.1.4 Embedding 与向量库存储

知识库写入完成后，Retriever 调用 `update()` 为缺失向量的 chunk 生成 embedding。默认模型路径为 `model/corpus/bge-small-zh-v1.5`。系统通过 SentenceTransformer 对 chunk 正文编码，并启用 `normalize_embeddings=True`，将生成结果转换为浮点向量。

`update()` 首先读取 `corpus.db` 中当前模型下的全部 chunk，再读取 `vector.db` 中已有的 chunk ID，只对缺失记录执行 embedding 编码。该过程支持增量更新，新论文归档后不需要重新计算全部历史向量。生成结果写入 `data/vector/vector.db` 的 `vectors` 表，表中保存 chunk ID、模型路径、向量 JSON、向量维度、正文哈希以及创建和更新时间，主键为 `(chunk_id, model_path)`。

当前 `vector.db` 使用 SQLite 保存向量，没有建立 HNSW、IVF 等近似最近邻索引。向量以 JSON 形式存储，检索时需要读取并反序列化当前模型的全部向量。因此，该设计适合原型和中小规模本地知识库。随着论文和 chunk 数量增长，系统需要使用 FAISS、Qdrant、Milvus 或 pgvector 等具有向量索引能力的存储方案，以降低检索延迟。

#### 2.1.5 BM25 与向量混合检索

用户提交 query 后，系统首先从 `vectors` 表读取当前模型下的所有向量记录，再根据 chunk ID 到 `corpus.db` 的 `chunks` 表回查正文和元数据。只有向量存在、知识库正文仍然存在并且模型路径一致的 chunk 才进入候选集。BM25 与向量检索使用同一批候选，因此尚未生成向量的 chunk 不会单独进入 BM25 检索。

向量检索将 query 编码为向量，并计算 query 向量 \(q\) 与每个 chunk 向量 \(d\) 的余弦相似度：

\[
\operatorname{cosine}(q,d)=\frac{q\cdot d}{\lVert q\rVert\lVert d\rVert}
\]

余弦相似度越高，表示 embedding 模型判断 query 与 chunk 的语义越接近。当前实现会对全部候选向量逐条计算相似度，而不是调用数据库中的近似向量搜索。

BM25 对 query 和候选 chunk 的正文进行词级处理。连续中文文本使用 jieba 精确模式分词，连续英文单词转换为小写，连续数字作为完整 token 保留，空白和标点被过滤。query 与 chunk 使用完全相同的分词逻辑。系统根据词频、文档频率、文档长度和平均文档长度计算 BM25，参数为 `k1 = 1.5`、`b = 0.75`。高频但普遍存在的词权重较低，能够区分候选的稀有专业术语权重较高。

向量相似度与 BM25 得分的数值范围不同。系统分别对两组分数进行 min-max 归一化，将分数映射到 0 至 1，然后计算混合分数：

\[
hybrid\_score=0.6\times vector\_score+0.4\times bm25\_score
\]

系统按混合分数降序排序，取前 `top_k` 个结果。每个结果包含 chunk ID、正文、元数据、模型路径、混合分数、向量分数和 BM25 分数。混合分数相同的情况下，系统优先选择归一化向量分数更高的 chunk，然后选择 chunk 顺序较早的记录。

`top_k` 只限制最终返回数量，不限制前面的候选计算。即使最终返回五个结果，当前实现仍然读取并评分当前模型下的全部有效候选。随着知识库规模扩大，BM25 应迁移到倒排索引，向量检索应迁移到近似最近邻索引。两路检索可以分别产生有限候选，再执行加权融合、RRF 或交叉编码器重排。

### 2.2 系统接口

#### 2.2.1 归档接口

归档接口为 `retriever.archive(path)`。输入参数是一个 PDF、TXT 或 DOCX 文件路径。接口首先执行路径和文件格式校验，再检查当前模型下是否已经存在相同来源键。对于新文档，接口调用 `process_document()`，完成文档读取、文本清洗、自然段恢复、初步语义分块、二次动态分块、元数据添加和知识库保存，随后调用 `update()` 补齐向量。

归档成功时，接口返回 `PipelineResult`，其中包含加载的文档、加载错误、自然段、语义块、最终 chunk 和数据库路径。重复文档返回 `None`。路径不存在、输入为目录、扩展名不受支持、PDF 解析失败或模型加载失败时，接口抛出异常，由上层程序转换为用户可读的错误信息。

#### 2.2.2 检索接口

检索接口为 `retriever.retrieve(query, k)`。`query` 是用户问题，`k` 是返回结果数量。接口执行候选加载、query embedding、余弦相似度计算、BM25 计算、分数归一化、加权融合和 top_k 排序，返回 `RetrievalResult` 列表。

每个 `RetrievalResult` 包含 `chunk_id`、`content`、`metadata`、`model_path`、`hybrid_score`、`vector_score` 和 `bm25_score`。当 `k < 1` 时接口抛出 `ValueError`，知识库为空或没有有效向量候选时返回空列表。检索接口只负责返回相关证据，不负责直接生成最终自然语言答案。

#### 2.2.3 MCP 接口

MCP 服务位于 `rag_mcp_server.py`。服务使用 FastMCP 创建，监听 `127.0.0.1:8001`，采用 streamable HTTP，服务路径为 `/mcp`，并设置为无状态 HTTP 模式。MCP 将本地 RAG 功能封装为工具，使支持 MCP 的智能体能够发现工具定义并在任务中调用。[10]

`archive_to_corpus(path)` 工具封装归档功能。它接收单个 PDF、TXT 或 DOCX 路径，调用 `retriever.archive()`，但不返回完整文档、段落和 chunk 正文。成功归档时只返回状态、来源文件名、来源键、文档数量、chunk 数量、加载错误数量和知识库路径；重复归档时返回 `skipped_duplicate` 状态和零计数。该设计可以控制 MCP 返回体大小，避免把整篇论文重复发送给客户端。

`get_RAG_result(command)` 工具封装检索功能。它接收一个完整查询，去除首尾空白后调用 `retriever.retrieve()`。当前 MCP 层固定 `TOP_K = 5`，将五个最相关 chunk 的正文按序号拼接后返回。如果没有检索结果，则返回知识库中未发现相关内容的提示。

当 MCP 客户端连接该服务后，LLM 可以根据工具名称、描述和输入参数判断是否调用归档或检索工具。例如，用户询问知识库中的 EEG 论文方法时，智能体可以调用 `get_RAG_result` 获取证据，再根据检索内容生成回答；用户要求加入一篇新论文时，智能体可以在获得合法文件路径和操作授权后调用 `archive_to_corpus`。工具能否被自主选择还取决于客户端配置、模型工具调用能力和系统提示，MCP 服务本身负责提供标准化能力，不负责决定最终智能体策略。

## 3. 技术可行性结论

当前项目已经完成论文知识库原型所需的主要技术环节。系统能够读取常见文本型论文文件，恢复自然段，执行两阶段分块，将 chunk 和来源元数据保存到 SQLite 知识库，并使用本地 embedding 模型建立增量向量记录。在线检索同时使用 BM25 精确词匹配和向量语义相似度，经独立归一化后按照 0.6 与 0.4 的权重融合，并返回最相关的 top_k 个文本段。MCP 服务进一步把归档和检索封装为智能体工具，形成了从论文输入到知识调用的完整链路。

该方案能够支持脑机接口与 EEG 论文的本地归档、检索和智能体问答，技术路线可行。当前实现的主要限制是 PDF 版面处理能力有限、英文论文与中文 query 之间存在 embedding 语言适配问题、向量和 BM25 均采用全候选内存计算、去重规则主要依赖文件名，以及检索结果缺少页码和正式引用信息。这些问题属于后续工程扩展，不影响原型闭环成立，但会影响大规模性能和科研回答的可核查性。

因此，本项目可以作为脑机接口与 EEG 领域 RAG 知识服务的基础实现。在中小规模论文库中，现有方案能够完成知识构建和混合检索；在扩大数据规模或用于正式科研服务之前，需要进一步完善文献元数据、跨语言模型评测、PDF 版面解析、数据库索引和引用追溯机制。
