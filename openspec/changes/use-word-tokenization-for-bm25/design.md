## Context

见 `proposal.md`。当前 `HybridRetriever/method.py` 的 `_char_tokens` 会丢弃空白后逐字符返回 token，BM25 的统计和公式直接依赖这些 token。`plan/HybridRetriever/method.txt` 现要求中文使用 jieba 精确模式，英文和数字使用连续单词规则，并要求查询与分块共用同一分词逻辑。

仓库当前没有 Python 依赖清单，因此本次引入 jieba 时还需要提供最小依赖声明和安装说明。

## Goals / Non-Goals

**Goals:**

- 提供一个供 query 和 chunk 共同调用的混合文本分词入口。
- 让中文词语、英文单词和连续数字成为 BM25 的统计单位。
- 保持 `bm25_search` 的签名、BM25 参数与返回结构不变。

**Non-Goals:**

- 不修改向量编码或余弦相似度计算。
- 不修改 Retriever 的候选集、分数归一化或 0.6/0.4 混合排序。
- 不增加停用词、同义词、词干提取或自定义 jieba 词典。

## Decisions

1. **先识别文本片段，再分词。** 使用正则表达式扫描连续中文、连续英文字母和连续数字片段；中文片段交给 `jieba.cut(..., cut_all=False)`，英文转小写，数字原样保留。其余字符视为分隔符，因此空白和标点不会进入 BM25。相比直接把整段文本交给 jieba，这能明确保证英文与数字的边界规则。

2. **query 与所有 chunk 复用同一个 token 函数。** `bm25_search` 只通过该入口生成 query terms 和 document terms，避免两侧预处理漂移。相比维护两个包装函数，共享入口更容易通过单元测试验证。

3. **jieba 是必需依赖，不进行字符级降级。** 缺少依赖时应在导入或调用阶段给出清晰错误，而不是静默回到旧行为，否则会违反计划定义的检索语义。仓库将增加最小 `requirements.txt` 声明和 README 安装命令。

## Risks / Trade-offs

- [jieba 的通用词典可能无法正确切分领域术语] → 本次保持默认词典，后续如需自定义词典应另建变更。
- [首次分词会加载词典并增加启动延迟] → jieba 在进程内缓存初始化结果，避免自行重复构建分词器。
- [词级切分会改变现有 BM25 分数和排序] → 这是预期行为；增加中英文混合测试并运行完整回归测试，确认接口和融合流程不变。

## Migration Plan

1. 安装新增的 jieba 依赖。
2. 部署更新后的分词实现；语料库和向量库无需迁移，因为 BM25 在查询时即时计算。
3. 如需回滚，恢复旧版代码和依赖即可，数据库结构及数据不受影响。
